feat(api): mount live gateway endpoint for real-time telemetry polling

The Omniroute gateway is now instantiated once per server process and reachable
over HTTP, so the UI reads the same telemetry a producer pushes.

=== THE GATEWAY IS A SINGLETON, AND THAT IS THE SUBSTANCE ===

The gateway holds the in-flight stream AND the counters the dashboard reads.
Built per request, a push would land in a broker discarded when the response was
written and every read would report "no data" forever. This is the same failure
`DynamicAgentRegistry` had before it was mounted, and the singleton shape is
repeated here on purpose rather than discovered again.

=== A RATE NEEDS TWO INSTANTS, AND THE SERVER IS WHERE THEY BOTH EXIST ===

`LiveVerdict` carries `records`: a COUNT from one snapshot, not a speed. That is
why every earlier throughput statement in this project was a guess and why the UI
refused to print one. The browser holds one instant; the server holds every
instant, because it is what is being polled.

So `ThroughputMeter` (platform/omniroute/throughput-meter.ts, 10 tests) measures
the rate from consecutive observations, and the reading travels with the verdict.
It is bounded -- it lives in a long-running server with a dashboard open.

Three properties are tested because each one is a way to be confidently wrong:

  - The FIRST observation returns null, not zero. One point is not a rate, and a
    zero there would read as "the stream has stopped", the opposite of the truth.
  - A stalled stream reports rate 0 WITH a live window. Zero-with-no-window is not
    information.
  - A gap between polls is not reported as one enormous burst. This is the exact
    failure a single-pair meter has, and the observed 14,901 ev/s over a 21.9s
    window on the first reading of a real flood is it working.

Every reading publishes its `windowMs`. A rate without its window is not a
measurement, it is a vibe.

=== TWO ROUTES, ONE OWNER ===

`GET /api/portal/live` and `POST /api/portal/ingest` live in portal-routes.ts,
not in a new service. They share the portal's credential, tenant boundary and
refusal rendering, and this module has already argued once that two owners for one
surface is how two policies slowly disagree.

The provider name is the ingress surface and is FIXED AT BOOT. Ingest refuses an
unconnected provider, because a caller must not be able to name a door the process
did not open.

Batches cap at 1000 events. Unbounded, that is an allocation sized by whoever sent
the request -- a denial-of-service reachable by anyone holding a credential.

Numeric field values are COERCED to strings, not refused. Every column in this
platform is a string and a producer sending `{ elapsed_time: 1200 }` has done
nothing wrong; refusing it would teach the producer to quote its numbers, which
is a workaround rather than a fix.
